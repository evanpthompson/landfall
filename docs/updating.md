# Updating Landfall

Until Landfall ships an OTA update path (planned post-beta — see "Future: OTA"
at the bottom of this doc), every update is a manual procedure. **Your data is
preserved** through all of these procedures because it lives in Docker volumes
that the image never touches.

---

## What survives every update

Docker named volumes hold the only state that must be preserved:

| Volume | Contains |
|---|---|
| `landfall_postgres_data` | All user state — profiles, layouts, linked accounts, cards, themes |
| `landfall_redis_data` | OTP rate-limit counters, ephemeral caches |
| `landfall_caddy_data` | TLS certificates from Let's Encrypt |
| `landfall_caddy_config` | Caddy's auto-generated runtime config |

The `.env` file at `/home/landfall/landfall/deploy/.env` also survives — that
holds the per-device secrets generated by `landfall-firstboot.service`. **Do
not delete it** unless you accept that all encrypted OAuth tokens will be
invalidated and every linked account will need to be reconnected.

What does *not* survive an image reflash:

- Anything you put outside `/home/landfall` (custom scripts, manual installs)
- WiFi credentials and hostname (re-apply via `configure.sh` before rebuilding)
- The display app's local SQLite cache (settings re-sync from server on first launch)

## Procedure A — Server-only update (most common)

Use this when:

- The Pi is healthy
- You want to update only the Landfall **server** (`landfall-server` container)
- You do not need a new Pi image

This is non-destructive and takes ~3 minutes.

```bash
# From a development host, cross-compile the new server image for arm64
bash deploy/pi-gen/build.sh --stage-only   # rebuilds the server tarball

# Copy the tarball to the Pi
scp deploy/pi-gen/work/pi-gen/stage2-landfall/00-landfall/files/landfall-server.tar.gz \
    landfall@<pi-hostname>.local:/tmp/

# On the Pi: load the new image and restart the server
ssh landfall@<pi-hostname>.local
sudo docker load < /tmp/landfall-server.tar.gz
cd ~/landfall/deploy
docker compose up -d server
docker compose ps   # confirm `server` is healthy
```

Postgres, Redis, and Caddy are untouched. The display reconnects automatically
within ~5 seconds once the server is back up.

## Procedure B — Display app update (Flutter changes only)

When the display binary changed but the server didn't:

```bash
# On the dev host
bash tools/scripts/build_linux.sh --arch arm64
scp -r apps/display/build/linux/arm64/release/bundle/* \
       landfall@<pi-hostname>.local:/home/landfall/landfall/display/

# On the Pi: just restart the graphical session
ssh landfall@<pi-hostname>.local
sudo systemctl restart lightdm
```

The openbox autostart relaunches the binary automatically.

## Procedure C — Full image reflash (major versions, kernel updates, security patches)

Use this for the first beta → GA cut, kernel updates, or any change to
`deploy/pi-gen/stage2-landfall/`. This is destructive to the SD card — but
**your data still survives** if you back up the Docker volumes first.

### 1. Back up the Pi's data

On the Pi:

```bash
ssh landfall@<pi-hostname>.local
cd ~/landfall/deploy
sudo systemctl stop landfall-server   # quiesce postgres

# Tar up the docker named volumes (lives at /var/lib/docker/volumes/)
sudo tar -C /var/lib/docker/volumes -czf ~/landfall-data-backup-$(date +%Y%m%d).tgz \
  landfall_postgres_data \
  landfall_redis_data \
  landfall_caddy_data \
  landfall_caddy_config

# Also save .env — it has the per-device secrets that decrypt OAuth tokens
sudo cp ~/landfall/deploy/.env ~/landfall-env-backup-$(date +%Y%m%d).env

# Pull both off the Pi
exit
scp landfall@<pi-hostname>.local:~/landfall-data-backup-*.tgz   ./
scp landfall@<pi-hostname>.local:~/landfall-env-backup-*.env    ./
```

### 2. Build and flash the new image

On the dev host:

```bash
bash deploy/pi-gen/configure.sh   # or use --from-env / --from-yaml
bash deploy/pi-gen/build.sh
```

Flash the resulting `.img` to the SD card with Raspberry Pi Imager. **Do not
fill in any Pi Imager customisation fields** — our image bakes everything in
via `configure.sh`. See `docs/raspberry_pi_guide.md` for full details.

### 3. Restore on first boot

The first boot of the new image will run `landfall-firstboot.service` which
**generates new secrets and writes a fresh `.env`**. Stop that from happening
by restoring your backup before the service runs:

```bash
# Boot the Pi (it will reach the firstboot service quickly)
# As soon as SSH is responsive, before the display has fully loaded:
ssh landfall@<pi-hostname>.local

# Stop firstboot mid-flight (it's idempotent — safe to interrupt)
sudo systemctl stop landfall-firstboot

# Restore your backed-up .env
scp <your-laptop>:~/landfall-env-backup-*.env /tmp/old.env
sudo cp /tmp/old.env ~/landfall/deploy/.env
sudo chown landfall:landfall ~/landfall/deploy/.env
sudo chmod 640 ~/landfall/deploy/.env

# Mark firstboot complete so it never reruns
sudo touch /var/lib/landfall/.initialized

# Restore the data volumes (Docker must NOT be running for this)
sudo systemctl stop docker
scp <your-laptop>:~/landfall-data-backup-*.tgz /tmp/
sudo rm -rf /var/lib/docker/volumes/landfall_*_data \
            /var/lib/docker/volumes/landfall_caddy_*
sudo tar -xzf /tmp/landfall-data-backup-*.tgz -C /var/lib/docker/volumes/

# Start everything back up
sudo systemctl start docker
sudo systemctl start landfall-server
```

### 4. Verify

```bash
landfall-doctor   # should report all green
```

If anything is broken, `landfall-bug-report` and the on-screen diagnostic will
walk you through next steps.

## Sanity checks before any update

```bash
ssh landfall@<pi-hostname>.local

# Are you about to update a Pi that's currently sick?
landfall-doctor

# What versions are currently running?
docker compose -f ~/landfall/deploy/docker-compose.prod.yml images
cat ~/landfall/landfall/display/version 2>/dev/null
```

If `landfall-doctor` is red, fix that first — never try to roll out an update
on top of an already-broken state.

## Future: OTA updates (post-beta)

Automatic over-the-air updates are deliberately deferred until **after the
beta** because they introduce real failure modes that need their own design
work:

- **Code signing** — whoever holds the release signing key can push code to
  every Pi in the wild. Key management policy (rotation, hardware-backed
  storage, who has access) has to be decided before any signing infrastructure
  is built.
- **A/B partitioning** — the only way to recover from a bad update without an
  operator SSH'ing in. The current pi-gen image layout doesn't have a B
  partition. Adding one means re-designing how `/boot/firmware/` and the root
  fs map to physical partitions.
- **Rollback policy** — what does the Pi do on the third failed boot of a new
  image? Auto-fall-back? Stay broken and show a diagnostic? That decision has
  to be made before code can be written.
- **Release server infrastructure** — somewhere to host signed manifests and
  image deltas, with availability + cost implications.

The placeholder script at `/opt/landfall/landfall-update.sh` exists so the
operator typing `landfall-update` discovers this doc rather than getting
"command not found." When OTA lands, that script will be replaced with the
real update orchestrator.
